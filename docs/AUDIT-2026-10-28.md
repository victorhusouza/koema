## F-01 — Initial briefing loading can discard edits

**Evidence:** `components/briefing-panel.tsx:77-88,91,125-130,157,163`.

The mount effect starts a briefing GET. The editor button and fields remain usable while loading. Typing sets the dirty flag and schedules a save after 650 ms. A delayed GET then unconditionally replaces content and clears the dirty flag. If it arrives before the timer, the pending save can observe a clean draft and skip the user's edit.

The test reviewer initially described overlapping date requests; the architecture reviewer independently identified the stronger initial-load/edit scenario above. Ordinary `selectDate` calls do have a loading guard, so normal sequential clicks should not be described as universally racing.

**Resolution:** Editing is disabled until the first briefing load completes. Loads also carry a request generation and captured draft version; a stale response cannot replace newer draft content. The same guard prevents an older date response from replacing a newer selection.

**Regression coverage:** `tests/briefing-load-guard.test.ts` resolves a deferred initial response after a newer draft version and verifies the old content is rejected; it also checks stale date response generations. It tests the shared guard directly because this repository has no DOM/component test runtime. Debounce, actual PUT after the deferred response, retry, close/Escape, and date transitions during save remain UI-level validation gaps.

## F-02 — Organizational labels cause false recurrence conflicts

**Evidence:** `lib/task-store.ts:24-32,164-169,267-270,359-367`.

The successor fingerprint contains the derived project label as well as area/project IDs. `get` hydrates current organizational labels. Renaming an area or project changes that hydrated label without editing the successor, while its predecessor retains the old fingerprint. Reopening the preceding occurrence can therefore prompt that the successor was edited even though the task content did not change.

Moving a project also changes its derived area; policy should explicitly distinguish that organizational change from direct edits to the task. This finding proves a false conflict, not silent data loss.

**Resolution:** Successor fingerprints use stable project/area IDs and omit derived display labels. A project move keeps the same project identity and does not look like a task edit; moving a task to another project or area still changes its destination identity. Schema migration v6 normalizes the saved fingerprint while preserving saved title, notes, checklist, dates, and other task content, so a real pre-migration edit still requires confirmation. The v4-to-v5 migration initializes periodic successor anchors from their predecessor.

**Regression coverage:** Recurrence tests cover project and area rename/move, actual successor title edits, v5 migration preservation of an earlier edit, and v4 weekly/monthly anchor migration followed by reopening.

## F-03 — Completed projects can receive open tasks

**Evidence:** `lib/task-store.ts:171-195,369-377`; task destination selectors in `app/prototype/page.tsx:204`.

Project completion rejects projects containing open tasks. Later task assignment validates project existence and area membership but does not check project status; completed projects are also offered by the task selector. Creating or moving an open task can thus leave a completed project containing unfinished work. The completion check and status update are separate statements, so their concurrency invariant also deserves a transactional test.

**Resolution:** Accepted product behavior per user clarification. Project completion and reopening remain manual, and users may assign tasks to completed projects. This finding is not a bug under the intended workflow.

No code change or lifecycle regression test was added for this accepted behavior.

## S-01 — Manual event origin validation needs verification

**Fingerprint:** `events-api:missing-origin-validation`

**Evidence:** `app/api/events/route.ts:20-25`; `app/api/events/[id]/route.ts:11-24`; contrast `app/api/calendar-feed/route.ts:18-19,30-31` and `lib/request-origin.ts:2-10`.

The original audit found that POST, PATCH, and DELETE event routes did not validate origin and POST parsed JSON irrespective of Content-Type. A hostile website is a lower-trust principal; the protected resource is the user's local manual appointments. A browser-permitted cross-origin POST with a safelisted text/plain body could therefore reach a write without the origin check used by other routes. Reading the response is not necessary to cause a mutation.

Two reviewers independently confirmed the missing source control. However, this run did not establish actual browser private-network/loopback permissions, preflight behavior, or a resulting mutation. POST is the clearest candidate; PATCH/DELETE normally require a preflight, so they must not be claimed exploitable merely because their source omits the check. The loopback binding limits network exposure. The intentionally absent login in the current single-user local application is not itself reported as an existing vulnerability.

**Resolution:** POST, PATCH, and DELETE now reject missing, malformed, mismatched, or external Origin values before parsing or opening SQLite. POST and PATCH require `application/json` (optional parameters such as `charset=utf-8` are accepted). DELETE has no body and does not require a media type. `localhost` request URLs paired with the actual `127.0.0.1` Host are accepted, matching the existing helper behavior. No CORS headers or blanket CORS policy were added.

**Regression coverage and limits:** Route tests use a temporary database and verify same-origin POST/PATCH/DELETE, the `localhost`/`127.0.0.1` alias, missing/malformed/external Origin rejection, JSON media type rejection, malformed JSON, and successful local mutations. No browser attack, hostile-origin request, real database, or calendar feed was used. This is a source-level correction with route regression evidence, not a browser reachability test or security certification; no vulnerability severity is assigned.

## Test coverage assessment

Existing source tests cover SQLite persistence, task completion/reopening, daily/weekly/monthly recurrence and shorter months, organizational migration, OAuth state/token handling, and representative iCal parsing. Main gaps:

1. **Briefing component lifecycle:** the load guard has direct unit coverage, but debounce, failed-save retry, persistence after the deferred response, date switching during save, and close/Escape still need a UI-level harness. No DOM/component test framework exists in the current toolchain.
2. **HTTP contracts:** event mutation origin, media type, malformed JSON, host alias, and successful write paths now have temp-database route coverage. Task and organization route status codes and recurrence conflict confirmation through HTTP remain untested.
3. **Recurrence migration:** v4 weekly/monthly anchor migration and reopen, v5 fingerprint normalization preserving real edits, and organization/recurrence interactions now have store-level regression tests.
4. **iCal boundaries:** tests now cover cross-midnight events, an explicit timezone crossing the Belem date boundary, permitted and rejected redirects, declared and streamed response-size limits, and normalized fetch failures. A real elapsed timeout and API-route error mapping remain untested. See `tests/google-ical.test.ts` and `lib/google-ical.ts`.
5. **Organization/project lifecycle:** F-02 has store-level coverage. F-03 is accepted manual behavior, not an outstanding test gap.

These are missing behavioral checks, not measured percentages or proof that all listed paths are broken.

## Documentation assessment

### D-01 — Consistent backup and recovery instructions

The README now documents stopping the app, SQLite `.backup` or an offline sidecar-aware copy, disposable restore verification, preservation of the original, and key handling. The calendar guide links to it and distinguishes encrypted calendar credentials from ordinary task, briefing, and event rows.

The instructions explicitly avoid live-main-file-only copies and deleting a live WAL.

### D-02 — Discoverability of storage overrides

`PAINEL_DB_PATH` is now listed in `.env.example` and documented in the README with its default, writable-path requirement, and independence from encryption-key settings.

Setup, Node.js requirements, loopback binding, core features, read-only iCal behavior, English repository text, and Portuguese UI are otherwise consistent in the reviewed public docs. No hosting instructions exist because hosting remains future work.

## Architecture assessment

Atomic task migrations and transactions around core recurring-task operations are useful foundations. Stable area/project IDs are preferable to textual identity; the F-02 correction removes derived display state from conflict detection. F-03 remains the intended manual project lifecycle.

`app/prototype/page.tsx` combines view routing, network calls, organization dialogs, tasks, and calendar state in a dense component. This is a maintainability risk rather than a separate proven functional defect. Extract domain-focused services/hooks and UI components incrementally while adding lifecycle tests. Avoid a broad rewrite before the identified invariants are fixed.

Before hosting, design authentication, external HTTPS/proxy origin handling, data/key backup, and operational recovery. Public source availability is not equivalent to making the current unauthenticated local server ready for Internet exposure.
